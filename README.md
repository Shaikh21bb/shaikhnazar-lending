# SHAIKH Industries — Sales Agent v1

Sales Agent использует базу знаний компании и отвечает через Telegram или WhatsApp. Облачный движок поддерживает историю, календарь и передачу менеджеру. Для WhatsApp через QR есть отдельный ручной локальный режим: Mac + Docker + n8n + Ollama, без платного LLM API. Возможности этих режимов отличаются; локальный режим пока не создаёт задачи календаря и не синхронизирует диалоги с сайтом.

## Что уже работает

- Telegram использует общий серверный Sales Agent вместо отдельного prompt-кода.
- OpenAI Responses API или Gemini выбираются через серверные env-переменные.
- История сохраняется в `agent_chats`, состояние клиента и handoff — в `customers`.
- Инструмент `create_followup` добавляет задачу в существующий календарь.
- `/api/followups/run` отправляет наступившие follow-up и помечает их выполненными.
- Инструмент `handoff_to_human` выключает автоответы для клиента и создаёт задачу менеджеру.
- Глобальный AI ON/OFF и ручной возврат клиента от человека к AI доступны в текущем интерфейсе.
- WhatsApp поддерживает два взаимоисключающих режима доставки: официальный Cloud API или отдельный QR-мост на постоянно работающем компьютере/сервере.
- В QR-режиме бот создаётся без токена в панели, QR виден только вошедшему пользователю панели, а новый агент остаётся AI OFF до обучения и подключения.
- `/api/sales/simulate` тестирует тот же движок локально без Telegram/WhatsApp.
- Публичные пути `/api/...` ведут через одну Vercel Function; обработчики лежат в `server/api/`. Так проект укладывается в лимит функций Hobby без изменения ссылок и вебхуков.

## Установка

1. Для новой базы выполните `supabase-migration-7.sql`, затем `supabase-migration-8-sales-agent.sql`. В существующем проекте Shaikh.digital миграция 8 уже применена; повторно запускать полную схему 7 не нужно.
2. Скопируйте `.env.example` в `.env.local` и заполните Supabase и один LLM provider.
3. Запустите проект через Vercel CLI или любой совместимый с Vercel Functions локальный runtime.
4. В панели создайте одного Sales Agent. Кнопка «Обучить» открывает базу знаний и шаблон сценария переписки. Включайте AI только после проверки ответов.

Минимум для LLM:

```env
SUPABASE_URL=...
SUPABASE_SERVICE_ROLE_KEY=...
LLM_PROVIDER=openai
OPENAI_API_KEY=...
OPENAI_MODEL=gpt-6-luna
OPENAI_REASONING_EFFORT=low
BUSINESS_TIMEZONE=Asia/Almaty
AUTH_SECRET=replace-with-at-least-32-random-characters
```

Ключ LLM используется только на сервере (`server/api/`) и никогда не отправляется во frontend.
API-вызовы OpenAI оплачиваются отдельно; бесплатный тариф для `gpt-6-luna` не заявлен. При необходимости можно выбрать Gemini через env, не меняя код агента.

## Локальная проверка без мессенджера

После создания Sales Agent в Supabase и входа в панель используйте `/api/sales/simulate` с cookie авторизованной сессии:

```bash
curl -X POST http://localhost:3000/api/sales/simulate \
  -H 'Content-Type: application/json' \
  -H 'Cookie: shaikh_session=<ваша_локальная_сессия>' \
  -d '{"customerId":"demo-1","customerName":"Айгуль","message":"Сколько стоит ваш продукт?"}'
```

Можно продолжать писать с тем же `customerId`: история сохранится. Для production endpoint выключен, если явно не задано `SALES_AGENT_DEV_MODE=true`.

## WhatsApp через QR (неофициальный вариант)

Этот режим использует [Baileys](https://github.com/WhiskeySockets/Baileys) как отдельное связанное устройство WhatsApp Web. Он **не поддерживается WhatsApp**: [WhatsApp предупреждает](https://faq.whatsapp.com/378279804439436/), что использование неофициальных приложений может привести к временной или постоянной блокировке номера. Не используйте для массовых рассылок. Компьютер/сервер с процессом должен оставаться включённым 24/7; Vercel не хранит длительное WhatsApp-соединение.

1. Примените `supabase-migration-10-whatsapp-qr.sql`. Таблицы QR и очереди закрыты от публичного доступа.
2. В Vercel задайте серверные переменные `WHATSAPP_DELIVERY_MODE=qr`, случайный `WHATSAPP_BRIDGE_SECRET` (32+ символов), `AUTH_SECRET`, `SUPABASE_URL` и секретный ключ Supabase. Не помещайте их в frontend.
3. На постоянно работающем компьютере создайте игнорируемый Git файл `.env.worker.local` с `BRIDGE_BASE_URL=https://ВАШ-ДОМЕН` и тем же `WHATSAPP_BRIDGE_SECRET`. Если WhatsApp-агентов несколько, укажите `BRIDGE_AGENT_ID` — UUID ровно того агента, которого нужно связать с номером.
4. На Mac с Docker Desktop и Ollama запустите `start-whatsapp.command` двойным щелчком (или `./start-whatsapp.command` в Терминале). Скрипт запускает локальные n8n, Ollama и WhatsApp-мост. По умолчанию выбрана `qwen3.5:9b-mlx`: из трёх установленных моделей она дала лучший результат на пробном диалоге. Ей требуется около 9 ГБ памяти; на 16-ГБ Mac другие тяжёлые программы могут замедлить ответы. Для быстрого, но менее точного варианта используйте `LOCAL_AGENT_MODEL=qwen3:1.7b ./start-whatsapp.command`, для третьего — `LOCAL_AGENT_MODEL=llama3.1:8b ./start-whatsapp.command`. При необходимости скрипт скачает выбранную модель. `stop-whatsapp.command` останавливает только эти сервисы, не трогая другие контейнеры. Ключи связанного устройства и локальная история сохраняются в Docker volume `whatsapp-session`, поэтому остановка не требует повторного QR. Docker Desktop и Mac должны работать, пока нужны ответы; спящий Mac не отвечает клиентам.
5. В панели откройте агента → «Подключить WhatsApp». Сканируйте появившийся QR в WhatsApp Business → «Связанные устройства». Файлы `.wa-session/` содержат ключи связанного устройства: храните их приватно и не отправляйте нам или в Git.
6. Для локального режима Vercel Production должен иметь `WHATSAPP_LOCAL_AGENT_ENABLED=true`. Это разрешает только отдавать базу знаний локальному мосту через защищённый серверный запрос. `WHATSAPP_MESSAGE_DELIVERY_ENABLED` остаётся `false`: облачный ИИ и облачная отправка выключены. Обучите агента в панели: «Обучить» → заполните «База знаний» конкретными фактами, приветствием, вопросами и запретами → сохраните проект и привяжите его к «Шаихназар». На сайте включите статус агента и AI ON. Без непустой базы знаний ответов не будет.
7. После обучения и теста включите локальные автоответы `./enable-sales-agent.command`; выключайте их без потери WhatsApp-связи через `./disable-sales-agent.command`. При первом запуске автоответы выключены. Остановить весь локальный стек можно `./stop-whatsapp.command`. n8n открыт только на этом Mac: `http://localhost:5678`. Не открывайте порт 5678 в интернет.

### Что видно в n8n и где обучать

На сайте теперь есть **Sales Studio**: выбор одной из установленных моделей Ollama, отдельные поля базы знаний и языка, проверка готовности WhatsApp/Mac/Ollama/обучения, единая кнопка включения или паузы ответов и тестовый чат. Кнопка на сайте меняет и AI-статус, и локальное разрешение ответов; Mac применяет команду при следующем обновлении (обычно до 10 секунд). Локальные `enable-sales-agent.command` / `disable-sales-agent.command` остаются ручным управлением; повтор старой команды с сайта не отменяет последующую локальную паузу. Для модели, выбранной на сайте, оставьте `modelChoice` в n8n как `{{ $json.model }}`.

Тестовый чат использует тот же сценарий n8n, локальную модель и материалы компании, но никогда не вызывает отправку в WhatsApp. Он доступен и при паузе автоответов. Тестовый запрос проходит через закрытую серверную очередь и доступен для выполнения/получения результата 3 минуты. Истёкшие записи очищаются при следующем тесте агента, а не автоматически по таймеру. Обычная история WhatsApp по-прежнему остаётся на Mac. Счётчик ответов на карточке показывает реальные успешные отправки с последнего запуска сервиса.

Для обновления существующей установки примените `supabase/migrations/20260926170505_local_agent_control.sql`, опубликуйте сервер и панель, затем запустите `./start-whatsapp.command`, чтобы пересобрать WhatsApp-мост. Настройки и временная тестовая очередь доступны только серверу; управление и тесты требуют подписанной сессии владельца.

Рабочий процесс **SHAIKH Sales Agent — локальный Ollama** теперь показывает всю цепочку: входящий webhook → материалы сайта и история клиента → выбор модели/дополнительные правила → подготовка запроса → Ollama → проверка ответа → ответ WhatsApp-мосту. Последний шаг **не отправляет сообщение напрямую в WhatsApp**: локальный мост получает ответ и отправляет его только при включённых AI на сайте и локальном переключателе.

- Основное обучение: сайт → **Агенты** → **Шаихназар** → **Обучить**. Нажмите «Добавить шаблон», заполните реальные сведения о компании, товарах, ценах, условиях, частых вопросах и желаемом сценарии (например, «если клиент просто поздоровался — спросить, что его интересует»). Сохраните проект, убедитесь, что он привязан к агенту, и включите AI. Это текстовая база знаний, а не загрузка PDF или дообучение весов модели. Новые материалы будут использованы в следующих сообщениях без перезапуска Docker.
- Выбор модели: сайт → карточка агента → **AI-модель**. Изменение применяется без перезапуска Docker. Настройка сайта имеет приоритет над `LOCAL_AGENT_MODEL` из скрипта запуска. В n8n в шаге **3. Выбор модели и доп. правила** оставьте `modelChoice` равным `{{ $json.model }}`: жёстко вписанное имя переопределит выбор сайта. Выбирайте только установленную в Ollama модель.
- Поле `extraRules` в том же шаге добавляет локальные указания к основным материалам сайта. Там удобно проверять короткую фразу или стиль, но постоянные факты о компании храните в «Обучить». После ручных правок в n8n сохраните и опубликуйте сценарий; локальный импорт при последующих запусках не перезаписывает его.

Автоответы сейчас по умолчанию выключены: сначала проверьте результат на учебном запросе, затем включайте их для клиентов.

Локальные диалоги хранятся только в Docker volume, а не в разделе «Диалоги» на сайте. Локальный режим **не выполняет** автоматические follow-up, задачи календаря и передачу менеджеру; бот не должен обещать такие действия. Для этих возможностей нужна отдельная защищённая синхронизация. Не включайте локальные автоответы для реальных клиентов, пока не проверите сценарий и защиту существующей базы знаний: старые таблицы проекта всё ещё доступны из браузера.

Проверка без клиента: отправьте тест в локальный n8n webhook с учебными данными; команда должна вернуть JSON с ответом модели:

```bash
curl http://127.0.0.1:5678/webhook/shaikh-sales-local \
  -H 'content-type: application/json' \
  -d '{"model":"qwen3.5:9b-mlx","context":{"enabled":true,"name":"Тестовый Sales Agent","language":"ru","knowledge":"Приветствие: Здравствуйте! Спросите, что интересует клиента."},"messages":[{"role":"system","content":"Ты тестовый Sales Agent. База знаний: Приветствие: Здравствуйте! Спросите, что интересует клиента."},{"role":"user","content":"Привет"}]}'
```

Локальная Ollama имеет HTTP API `http://localhost:11434/api` на Mac и `http://host.docker.internal:11434/api` внутри n8n Docker. **API-ключ для локальной модели не нужен**. Проверить установленные модели: `curl http://localhost:11434/api/tags`. Окно «Connect a model» у встроенного n8n Assistant — отдельная облачная функция и не настраивает этот WhatsApp-сценарий; не вводите туда ключи сайта или WhatsApp.

Для просмотра состояния: `docker compose -f compose.whatsapp.yaml ps` и `docker compose -f compose.whatsapp.yaml logs --tail=50 whatsapp-bridge n8n`. Не публикуйте логи с личными данными клиентов.

Если процесс остановится, входящие сообщения не будут автоматически обрабатываться. В локальном режиме Ollama нет платы за LLM API; нужны работающий Mac, электричество и интернет. Облачный режим имеет отдельные условия и может тарифицироваться.

## WhatsApp Cloud API (официальная альтернатива)

Нужны Meta Business / Developer App и WhatsApp Cloud API:

1. Получите permanent access token и Phone Number ID.
2. Добавьте env из секции `WHATSAPP_*` в `.env.example`.
3. В Meta укажите callback URL `https://ВАШ-ДОМЕН/api/webhooks/whatsapp` и тот же `WHATSAPP_VERIFY_TOKEN`.
4. Подпишитесь на событие `messages`.
5. Укажите UUID WhatsApp-агента в `WHATSAPP_AGENT_ID` (необязательно, если он один).
6. Для follow-up позже 24 часов создайте и одобрите в Meta шаблон с одной переменной в body, затем задайте `WHATSAPP_FOLLOWUP_TEMPLATE_NAME` и язык шаблона.

Для входящих webhook проверяется подпись `X-Hub-Signature-256`. Для локальной разработки Meta и платный провайдер не нужны: используйте симулятор.

## Follow-up 24/7

Миграция 9 устанавливает Supabase Cron, который проверяет наступившие follow-up каждые пять минут. Пока секреты не заданы, задание ничего не отправляет. Для включения в Supabase Vault создайте `sales_agent_followup_url` со значением `https://shaikh.digital/api/followups/run` и `sales_agent_cron_secret` со значением того же `CRON_SECRET`, который настроен в Vercel. Секреты не записывайте в Git.

Vercel Hobby поддерживает расписания не чаще одного раза в сутки, поэтому частые follow-up вынесены в Supabase Cron. Endpoint принимает:

```text
Authorization: Bearer <CRON_SECRET>
```

## Важное про текущую авторизацию

Существующий проект использует собственную таблицу `managers_auth`. Новые пароли сохраняются в виде scrypt-хеша; старые обновляются при успешном входе или смене через панель владельца. Панель больше не показывает пароли и требует подписанную HttpOnly-сессию с ролью владельца. Логины `Shaikh` и `admin` имеют роль владельца, остальные должны совпадать с именем менеджера. Публичный доступ к `managers_auth` в основной базе закрыт миграцией 11; другие старые таблицы ещё используют браузерный доступ и требуют отдельного переноса за серверную проверку доступа. Поэтому не вводите конфиденциальную базу знаний и не включайте реальных ботов до закрытия оставшихся публичных политик. Для production обязательно настроить `AUTH_SECRET` и серверный ключ Supabase; LLM/WhatsApp secrets не должны попадать во frontend.

После публикации серверного входа и проверки `SUPABASE_SERVICE_ROLE_KEY` в Production примените `supabase-migration-11-auth-privacy.sql`: она закрывает анонимный доступ к таблице аккаунтов. Не запускайте миграцию до новой серверной версии — старый вход из браузера перестанет работать.
